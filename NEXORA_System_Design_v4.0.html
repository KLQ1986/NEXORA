1. Purpose and Scope

NEXORA is a personal, local-first system that produces video with as much automation as is practical while the operator keeps control of every decision that matters. This is the consolidated edition of its design. It replaces the earlier editions (v1.0 to v3.3), which grew by addition; here every topic appears once, in one vocabulary. Nothing in this document has been implemented or validated yet.

1.2 What the system does

  • Understands the operator's footage and makes every moment searchable as text.
  • Turns an idea into a script, and the script into a list of shots.
  • Finds, for each shot, the right range inside the operator's footage, or sources it from stock or generation.
  • Assembles a timeline and finishes it: narration, captions, graphics, picture correction, music and mix.
  • Checks the result, shows the operator what needs a decision, and renders.
  • Exports or publishes, and records what was used so that every published video can be traced to its sources.

2. Design Principles

  • One source of truth: every record exists once, in NEXORA's own database.
  • The service drives the pipeline; models and agents work inside stages and never decide what runs next.
  • Deterministic where possible: media processing, state and cost are repeatable; model output is treated as uncertain and is checked.
  • Human in the loop: the operator approves what is published, and reviews by exception rather than everything.
  • Recoverable: state, retries, time limits and idempotency are designed in, because a personal Mac sleeps, restarts and runs out of disk.
  • Replaceable parts: every tool, model and platform sits behind one adapter contract.
  • Local-first and private by default: the operator's footage leaves the machine only when the operator allows it.
  • Non-destructive: source media is never modified; every edit is a new version.
  • Traceable: any output can be followed back to its sources, models, settings and approvals.
  • Reuse before rebuild, and small before large: borrow proven designs and tools, and add infrastructure only when a measured need appears.
  • Evidence before expansion: a capability earns its place by reducing a measured bottleneck.

4.4 Dependency rules

  • A layer may call any lower layer and never a higher one.
  • The Experience layer reaches the system only through the API.
  • Domain modules do not call each other. They exchange work through the timeline and shared records, and register their stages with the Orchestrator. The flow is Planning → Sourcing → Edit → Quality → Distribution; Library serves Sourcing and Edit.
  • Dependency inversion: a domain module defines the interface it needs, and an adapter implements it. No domain module imports a provider SDK or a tool binding.
  • Every model call goes through the Model Router.
  • Data is read and written through repositories.
  • Policy and budget are enforced in the Platform core when a stage is dispatched, so scheduled and internally spawned work is checked exactly like an API request. The API layer performs authentication and input validation only.
  • These rules are checked automatically by an import-rule linter in the test suite.

5. Platform Core

5.1 Role

The Platform core is the pipeline runtime. It decides operational matters — which step runs next and when, whether to retry or stop, whether budget remains, which model to call. It does not decide content matters such as what a video says or which clip fits a line; those belong to the domain modules and the models they call. Operational behaviour must be deterministic and testable, while model output is not; keeping the core ignorant of video stops the uncertain part from leaking into the part that must be certain.

5.2 Responsibilities

5.3 Membership test

A piece of code belongs in the Platform core if it would still be used unchanged when the product changed from video to another medium. Otherwise it belongs in a domain module.

5.4 Worked example

  • The operator ingests twenty self-shot videos. The Library module declares the stages: proxy, shot detection, frame description, summaries, index.
  • The core runs two videos at a time to protect memory.
  • The machine sleeps during video seven. On wake the core finds video seven stopped at frame description and continues from there; the first six are not processed again.
  • Video twelve is a corrupted file. The core retries twice, marks it failed with a reason, and moves on.
  • Each model call is costed. When the daily budget is reached, the core stops and notifies the operator.
  • When a new module is added later, it only declares its stages; queueing, recovery, retry and budget already exist.

6.5 Rules

  • Claiming: a worker claims a ready stage by compare-and-swap inside one SQLite write transaction. The claim has an expiry and is extended by heartbeat. One writer wins; the others see no change.
  • Atomicity: a state change and its event are written in the same transaction.
  • Success requires proof: a stage becomes succeeded only after its outputs exist, pass validation and are registered with a checksum.
  • Effect class: every stage declares one of three classes — pure (no external effect; retry freely), idempotent-external (safe to retry with the same idempotency key), non-idempotent-external (for example publishing; never retried without reconciliation).
  • Recovery at start-up and on wake: for each running attempt, check that the worker is alive (process id plus process start time) and its heartbeat is fresh. If not, a pure stage is marked crashed and retried; any other stage is marked unknown and reconciled through its adapter.
  • Retry: each stage has max_attempts and exponential backoff. Reaching the limit moves the stage to blocked, not to an endless loop.
  • Policy and budget: checked when a stage is dispatched. A denial moves the stage to blocked with the reason.
  • Cancellation: the request is recorded first. A running attempt stops at its next safe checkpoint, and its adapter is asked to cancel any external job.
  • Kill switch: no stage with a cost or an external effect is claimed while it is on. Reading status always works.
  • Idempotent submission: a run submitted twice with the same idempotency key is one run.
  • History: attempts are never overwritten. A manual retry of a blocked or failed stage creates a new attempt.

7.4 Rules

  • An adapter never writes records and never decides whether to retry. It reports; the core decides.
  • Outputs are written only to a staging area. The core validates them, computes checksums and registers them as asset versions.
  • After submit returns a handle, the core stores the external reference before waiting, so a crash cannot orphan a provider job.
  • Local tools such as FFmpeg run as child processes with a timeout, captured logs and exit status. reconcile for a local tool inspects the output file and the process.
  • An adapter declares whether it is local or cloud. The Model Router refuses to send a local-only asset to a cloud adapter.
  • Usage and cost are reported with every result, including failed ones that were billed.
  • Provider-specific response shapes never leave the adapter.

8.3 Versioning and immutability rules

  • An AssetVersion is immutable and identified by its checksum. New content is a new version; a file is never overwritten.
  • Script and Timeline are versioned documents. An edit creates a new version, and an approved version is frozen.
  • A Review binds to the version and checksum it approved. If the content changes, the approval no longer applies.
  • A TimelineItem references an AssetVersion, not an Asset, so that a render can always be reproduced.
  • Derived data — moments, understanding, embeddings — is keyed by (asset checksum, analyzer version, configuration hash) and is regenerated rather than edited. Human corrections are separate records that survive regeneration.
  • Lineage is complete by construction: parent versions and the creating attempt trace any published video back to its sources, models and settings.
  • Rights and privacy propagate: a derived asset takes the most restrictive status of its parents.
  • Identifiers are opaque, type-prefixed and never reused. A file path is never an identity.
  • Records are archived, not deleted. Media files are removed only by the retention policy, and their lineage rows remain.
  • Every record carries created_at, its creator (an attempt or the operator) and a schema version.

8.4 Storage

  • One SQLite database in WAL mode holds all records, the full-text index and the vectors. All writes go through repositories.
  • Original footage is referenced in place and identified by checksum; it is not copied into a managed store, to save disk.
  • Derived and generated files live in a managed media directory addressed by checksum.

Rule: an agent works inside a stage; the pipeline does not live inside an agent.

Orchestrator (Platform core) +-- Stage "Write script" <- core starts it, sets limits, records the result +-- Agent group: Scriptwriter -> Fact-checker -> Creative Director +-- each agent calls models through the Model Router

  • Bounded: maximum review rounds, cost ceiling and timeout are applied by the core, not left to the agents.
  • Granted tools only: search the footage library, read the script, look things up. No shell and no publishing rights.
  • Structured output: a script, a source list, a score. Agents do not write job state directly.
  • One context per agent: hand-offs carry a compact summary, not the whole conversation.
  • Use agents where reasoning and opposing views help: research, script writing and critique, fact-checking, judging footage candidates, reviewing a cut.
  • Do not use agents for deterministic work: proxies, shot detection, render, audio mix, publishing.

10. Local Operation, Privacy and Security

Decision of 2026-10-11: security work is deferred. The system runs locally on the operator's own Mac for a single operator.

  • Baseline: the API listens on the loopback address only and is not exposed to the network. No authentication is implemented.
  • Deferred: API tokens, a threat model, and hardening of secret storage.
  • Revisit before any of the following: exposing the API beyond the local machine, a messaging gateway or remote approval, a worker on another machine, a second user, or unattended publishing.

10.1 Privacy

  • Every asset has a privacy class: local-only or cloud-allowed. The operator's own material is local-only until the operator opts in.
  • The Model Router refuses to send a local-only asset to a cloud adapter; every adapter declares whether it is local or cloud (Section 7).
  • Retrieved web pages, transcripts and file metadata are treated as untrusted data and can never change tools, policy or destinations.

10.2 Constraints of a personal Mac

  • The machine sleeps and restarts. On wake and at start-up the Platform core runs recovery (Section 6.5).
  • Free disk is checked before ingest and before render; only derived and temporary files are ever cleaned, under the retention policy.
  • Long media work runs in child processes with time limits; orphaned processes are found and stopped.
  • One heavy model runs at a time on a 24 GB machine.
  • The database and critical metadata are backed up; media backup is tiered by value.

14.7.2 How a tool is called

  • Each OpenMontage tool runs in a separate child process with its own Python environment. NEXORA sends the request as JSON and receives the result as JSON.
  • OpenMontage is pinned to a specific commit and upgraded deliberately, never automatically.
  • A NEXORA adapter wraps the call and supplies what Section 7 requires and the tool lacks: a time limit, cancellation by stopping the process, a cost record taken from the tool's result, and normalised errors.
  • The tool is told where to write. Outputs go to the staging area; NEXORA validates them, computes checksums and registers them as asset versions.
  • Credentials are passed to the child process for that call only. The OpenMontage environment file is not used.
  • All code that touches OpenMontage lives in one package, so that it can be replaced as a unit.

Separate processes give three benefits: the heavy dependencies of OpenMontage do not mix with NEXORA's, a tool that hangs cannot take the system down, and all AGPL code sits in one place.

  • Replacing the OpenMontage package with another implementation of the same adapters requires no change in any domain module.

16. Planning

Planning turns an intent into an approved script made of shots. It is where reasoning and creative judgement are concentrated, so it is also where bounded agents are used.

16.1 Research and evidence

  • Work starts from the operator's brief, or from topics the system proposes inside configured limits of channel, audience, language and budget.
  • Research gathers sources with their publisher, date, retrieval time and the passage that supports each claim.
  • Verified facts, hypotheses, opinion and invention are kept apart; a factual claim without a source is flagged.
  • Ideas are scored on a visible scorecard — audience fit, evidence, freshness, differentiation, production feasibility, cost, and risk — and a risk can block an idea, not merely lower its score.
  • Research briefs are kept and linked to the scripts, videos and results that came from them, so research is not repeated.

16.2 Structured script

  • A script is structured data: scenes and shots with identifiers, intent, target duration, visual brief, spoken text, on-screen text and sound cues.
  • Each shot links to its need, its selected picture, its timeline items and its QC results.
  • Scripts are versioned. Alternate openings, endings and lengths are versions, not copies of the project.
  • Continuity checks cover recurring people or characters, wardrobe, location, props, style, voice and chronology.
  • Story quality is reviewed by the operator where a model score is not enough.

16.3 Brand and channel profiles

  • A brand profile is a versioned description of a channel or series: audience, voice, pacing, palette, typography, logo rules, caption style, narration style, pronunciation dictionary, banned phrases, and examples of accepted and rejected work.
  • A channel profile adds the destination: platform, formats, safe areas, loudness target, cadence, allowed and restricted topics, and publishing policy.

16.4 Format templates

A format template is the reusable definition of one kind of video. Without it every project decides structure, pacing and style again from nothing. A template is data, not code; it is versioned, and a project records the template version it used. Automatic generation of variants from a template is deferred.

  • Moments are grouped by theme, place, time and shooting session, with attention to footage that has never been used (17.5).
  • Each proposal is an IdeaCandidate (16.1) with a title, an angle, a fitting format template, the moments that would carry it, the share of shots the existing footage covers, the expected gaps and an estimated duration.
  • Proposals are scored on footage coverage, freshness, novelty against published videos, and fit with the brand profile.
  • Triggers: after a new session is ingested, on request, and periodically.
  • An accepted proposal becomes a pre-filled brief and enters pipeline B at stage 1.
  • The work is done by a bounded agent in the Strategist role (16.5, 9).

17. Library

The Library is the single store of everything the system can use as material — the operator's footage and photographs, stock that was fetched, clips that were generated, and music — together with what the system understands about it.

17.1 Storage volumes, offline media and automatic ingest

17.1.1 Volumes

  • A StorageVolume is a disk known to the system: internal, external or network. An asset version's location is a volume plus a relative path, never an absolute path.
  • Originals stay where they are (8.4). Proxies, thumbnails, understanding and embeddings are kept on the internal managed store, so that search, matching, preview and rough cut all work while the originals are offline.
  • A final render needs the originals. If a required volume is offline, the render stage becomes blocked with the list of volumes to connect. A draft render from proxies is available and is marked as draft.
  • Relinking: when a volume appears at a new path or files were moved, assets are recognised by a quick fingerprint (size plus partial hash) and confirmed by full checksum.
  • A missing-media report lists assets whose originals can no longer be found on any known volume.
  • Free space is checked before ingest and before render. Proxy size is governed by a policy that must be set from measured sizes per hour of footage.

17.1.2 Automatic ingest

  • Watch folders and volume-mount detection start an ingest run when new media appears.
  • A file is ingested only after it has stopped changing, so that a copy in progress is not read.
  • Duplicates are recognised by checksum and linked, not ingested twice.
  • An ingest preset per source sets the CameraProfile, the privacy class and the analysis tier.
  • After a session is ingested, the operator is asked once for the optional session note of Section 17.2.8.

17.2.3 Frame coverage policy

Requirement: every frame of a video must be resolvable to a description. Coverage is therefore defined as follows: every timestamp maps to exactly one FrameObservation whose valid range contains it. Describing literally every frame with a vision model is supported, but it is rarely justified — consecutive frames are nearly identical, and a 10-minute clip at 30 frames per second contains 18,000 frames.

  • Cheap signals are computed on every decoded frame of the proxy: scene-change score, motion magnitude, blur and exposure, perceptual hash. These need no model call.
  • Adaptive sampling chooses the frames sent to the vision model: the first frame of each shot, a base rate (default one frame per second, configurable), and extra samples wherever the cheap signals show a change such as a new object, a camera move or text appearing.
  • Each described frame owns the time range up to the next described frame. Ranges with no visual change are merged instead of being described again.
  • Exhaustive mode describes every Nth frame, down to N = 1, for a chosen asset or time range. A cost and time estimate is shown and checked against the budget before it runs.

17.2.5 Text storage and search

  • Every level is stored as plain text with asset_id, level, t_start and t_end. Search returns time-coded hits grouped video → segment → frame, each with a thumbnail and a jump-to-timestamp link.
  • description_language is configurable (for example Vietnamese). Transcripts stay in the spoken language. An optional second-language copy lets queries in either language match.
  • Text embeddings of the generated descriptions are stored beside the full-text index, because the wording of a script rarely matches the wording of a caption (18.2). At personal-library scale they are searched in-process; no separate vector database is introduced.
  • The operator can correct any generated text. Corrections are marked source = human, are never overwritten by re-analysis, and rank above model text.
  • Frame- and segment-level results feed Script-to-Footage Matching (18.2), Asset Discovery (18.3), the rough cut (19.1) and reframing (19.3).

17.2.6 Execution, privacy and cost

  • Each asset carries a privacy_class: local-only or cloud-allowed. Self-shot footage defaults to local-only until the operator opts in. The Model Router must honour this class, and a local-only asset must never reach a cloud provider.
  • Local speech and vision models for Apple Silicon are candidates only. They must be benchmarked for speed and for accuracy in the operator's language before the design depends on them.
  • Analysis is a run with a checkpoint after each stage and resumes after restart, sleep or low disk.
  • Results are cached by (checksum, analyzer_version, config_hash). Re-analysis runs only when one of these changes.
  • Before a run, the service estimates frames to describe × unit cost and time, and rejects a run that exceeds the budget. Analysis uses a low-priority background queue.
  • Proxies are disposable under the retention policy. The text understanding is small and is kept.

17.2.7 Accuracy controls

  • Every generated description stores model and prompt version and a confidence value.
  • Segment and video summaries cite their evidence (frame observation and transcript segment IDs). A statement without evidence is dropped or flagged.
  • People are not identified by default. They are described generically unless the operator labels them, subject to the consent rules of Sections 20.3 and 20.3.
  • Quality is measured with a labelled query set (precision@k) and sampled human review of captions. Thresholds are provisional until measured.

17.2.8 Visual-only footage

Much of the operator's footage may have no audio track, or audio with no speech. Understanding must then come from the picture alone. The design treats this as a normal case, not an exception: no stage may depend on a transcript.

  • Audio check at ingest: an absent audio track, silence or audio without speech is detected, and the speech stages are skipped rather than failed. Ambient sound, when present, is still labelled (wind, traffic, crowd) as weak context.
  • Motion-aware description: the vision model receives short ordered frame sequences covering a few seconds, not isolated frames, so that it can describe actions and changes — what is happening, not only what is visible.
  • Visual segmentation: moment boundaries come from visual change — a shift in image-embedding similarity between consecutive samples, camera motion, a subject entering or leaving — and are confirmed by the vision model.
  • Image-text embeddings of keyframes are part of the baseline index, so that a script line can be matched against the picture directly, independent of caption wording or caption errors.

17.3 Still images as source material

  • The operator's photographs are ingested into the Library like footage: checksum, capture date, location and device from their metadata, and volume and session.
  • Each image is understood as text — caption, objects, people count, setting, visible text — and receives text and image-text embeddings. In the index an image is a moment without a time range.
  • Matching (18.2) treats images as candidates of role still. The format template sets the largest share of stills a video may contain.
  • On the timeline a still receives a camera move — a pan or zoom path computed from its subject, reusing the subject detection of Section 19.3 — and a duration taken from the narration.
  • Phone formats are converted at ingest, orientation is honoured, and HDR photographs are tone-mapped as in Section 19.9.1. A photograph with an attached short clip is ingested as video.
  • A photograph may also be the first frame for image-to-video generation (18.4); the result is then a generated asset and carries the synthetic-content disclosure.
  • The whole-video review scores stills risk (20.2), so that a video does not turn into a slideshow.

17.4 Music library understanding

  • Music the operator owns or has licensed is ingested as assets of kind music, each with its licence record.
  • Analysis produces: duration, tempo, beat grid, sections (intro, build, peak, close) from changes in energy, loudness, whether vocals are present, and mood, genre and instrument labels with a short text description.
  • The description is indexed as text and embedded, so music is searchable in words like footage.
  • A MusicBrief (19.10) is matched against this index: filtered by tempo range, duration and vocal policy, ranked by mood, and fitted using the section boundaries.
  • The beat grid feeds cut snapping (19.2).
  • Usage is tracked so that one track is not repeated across consecutive videos, and a licence that has expired removes the track from matching.
  • The analysis tools and the audio-labelling model are candidates to be verified.

17.5 Library extras

  • Find similar: from any moment, list the nearest moments by image-text embedding. This reuses the index of Section 17.2 and needs no new analysis.
  • Usage tracking: a UsageRecord is derived from the timeline items of every published render. The library can show which footage has never been used.
  • Reuse policy: matching (18.2) applies a configurable penalty to moments used recently in other videos, so that the same clip does not appear everywhere.
  • Ratings: the operator can mark a moment as favourite or as rejected. Matching treats this as a prior; a rejected moment is never proposed.
  • Collections: named groups of assets or moments chosen by the operator, usable as a search filter and as a restriction for matching.

18.2 Script-to-footage matching

Purpose: given an approved script, select from the operator's footage library the clips that fit each line — by meaning and context, not by file name or keyword. Deep Video Understanding (17.2) exists to serve this capability.

18.2.1 Principle

Script and footage are translated into the same structured description and then compared in stages: broad recall first, careful judgement second, selection across the whole sequence last. Every match is explainable: which requirement of the script line was met by which evidence in the footage.

18.2.2 What the index must contain

  • Candidate moments: segments are subdivided into moments of usable clip length (configurable, for example 2–20 seconds) with stable content. Boundaries are placed where the content changes — a new action, subject, topic or camera move — even inside one continuous take with no cuts. Matching returns moments, not whole files: from a recording of several minutes, only the few seconds that fit the script line are selected.
  • Role: each moment is classified as a-roll (a person speaking to camera, matched by what is said) or b-roll (matched by what is shown), with finer labels such as establishing, detail, reaction and transition.
  • Descriptors: subjects, actions, setting, time of day, mood, shot size, camera movement and visual quality.
  • Context inheritance: the search text of each moment carries the meaning of its parent segment and the context of its video — where, when and why it was filmed — because the same picture can mean different things in different videos.
  • Text embeddings of the moment descriptions are stored beside the full-text index. Image-text embeddings of keyframes are stored as well, so that footage without speech can be matched on the picture directly (17.2.8).

18.3 References and continuity for generated shots

  • Approved character sheets, location references, product references and style guides are stored as asset versions and passed to generation.
  • Each scene lists its invariants — what must not change between shots. A violation of an invariant blocks a candidate.
  • References are reused across the episodes of a series.

18.4 Keyframe-first generation

  • A generated shot starts from an approved still image. Images cost far less than video, so mistakes in composition, character and style are caught before video is paid for.
  • The still is generated with the approved character, location and style references (18.3) and reviewed on the filmstrip of the board.
  • The approved still is the first frame for image-to-video generation and the continuity anchor of the shot. For a split shot, the last frame of one sub-shot is the first frame of the next (18.6).
  • A correction at the still stage — pose, framing, wardrobe — is made by editing the PromptSpec (18.5) and regenerating the still only.
  • Exception: when a provider offers text-to-video only, a small number of low-resolution drafts replaces the still.

18.8 Enhancement and character models

18.8.1 Upscaling and frame interpolation

  • Generation providers often return clips below the output specification in resolution or frame rate. An enhancement stage brings a clip up to the specification.

  • The enhanced clip is a new asset version whose parent is the provider's output.
  • QC checks for added artefacts, flicker and changes of identity; a failed enhancement falls back to the original with a recorded limitation.
  • Enhancement models, local or cloud, are candidates to be verified through the adapter conformance tests.

18.8.2 Character model training (P2)

  • Entry condition: a recurring series, and a measured continuity violation rate (Section 18.7) that reference images alone cannot bring under the threshold.

  • A CharacterModel is versioned and records its training set, provider, settings, and the rights and consent that cover it.
  • A new model version passes the continuity evaluation before the Model Router may use it.

19.3 Subject-aware reframing and multi-source sync

19.3.1 Subject-aware reframing

  • Subject tracks (face, person or salient object) are computed on the proxy as part of tier T3 analysis.
  • A ReframePlan is a keyframed crop window per target aspect ratio (9:16, 1:1, 4:5, 16:9), stored as a transform on the timeline items.
  • The crop path is smoothed with a dead zone and limits on pan speed and acceleration, to avoid jitter.
  • Modes: static crop, tracked pan, two-subject split or alternation, and fit-with-background when the subject cannot be held in frame.
  • The plan respects platform safe areas and caption zones from the channel profile.
  • QC measures the share of frames with the subject inside the crop, crop jitter and cut-off text. Failures go to review. The original framing is never overwritten.

19.3.2 Multi-camera and external-audio sync

  • Offsets between sources are computed by audio cross-correlation; embedded timecode is used when present.
  • Drift on long recordings is detected and corrected with piecewise offsets.
  • A SyncGroup stores member assets, offsets, drift and confidence. Low confidence requires human confirmation.
  • When an external recorder is present, its audio is the master track.
  • Angle selection rules (active speaker, wide shot on overlap) produce edit operations. Alternatively, a synced multi-camera timeline is handed to Resolve where that path has been validated.

19.4 Narration for footage without speech

When footage carries no speech, the narration is the spine of the video. Narration is produced before the picture is cut, because its timing decides how long each clip must be.

  • A narration line is a DialogueLine (19.5) spoken by a narrator. The narrator has a CharacterVoiceProfile: a synthetic voice, a licensed voice, or the operator's own recorded voice.
  • Order of work: approve the script → produce narration audio with word timings → derive each shot's duration → match footage (18.2) → cut.
  • The operator may record narration instead. The recording is aligned to the script by speech recognition, and lines that differ from the script are flagged.
  • The pronunciation dictionary of the brand profile (16.3) applies to names and foreign words.
  • Synthetic voice quality in the operator's language is unverified and must be benchmarked before a voice is fixed in a template.

19.6 The operator's own voice

  • Purpose: narration in the operator's own voice without recording every script.
  • Consent: by default only the operator's own voice may be cloned. A consent statement and the sample recordings are stored. Any other person's voice requires their documented consent (20.3).
  • Creation: a guided recording session in quiet conditions; the samples are checked for noise and clipping; the voice is created with a provider or a local model, both candidates to be verified.
  • The result is a CharacterVoiceProfile with voice source cloned, a consent reference and the provider's terms recorded.
  • Sending voice samples to a cloud provider is a privacy decision: the profile is created only if the operator allows it, and the procedure to delete the voice at the provider is recorded.
  • Evaluation before use: similarity and intelligibility by listening, and pronunciation in the operator's language with the pronunciation dictionary (16.3).
  • The cloned voice is usable only in the operator's projects, and synthetic-voice disclosure is applied where a platform requires it.
  • Fallback: narration recorded by the operator and aligned to the script (19.4).

19.7 Captions and subtitles

  • Text source: for narration and dialogue, the approved line text with its word timings, which is exact. For speech in footage, the transcript with word timestamps, corrected by the operator where needed.
  • Segmentation rules come from the template: maximum characters per line, maximum lines, minimum and maximum display time, breaks at phrase boundaries, no single orphaned word.
  • A CaptionStyle fixes font, size, colour, outline or background, position and the safe area. The font must cover the diacritics of the caption language.
  • Short-form styles may highlight the current word; this needs word timings and is part of the style.
  • Output: captions burned into the picture for short-form, and a sidecar file (SRT or VTT) for platforms that accept one. Both come from the same CaptionTrack.
  • Translated captions (P1) are a new CaptionTrack in another language, produced by a model and reviewed before use.
  • Operator corrections are stored on the CaptionTrack and survive re-rendering.
  • QC applies the subtitle row of Section 20.1: timing, readability, overflow, spelling and safe area.

  • Every source is conformed to the project's working format before it is cut: constant frame rate, working resolution, and one working colour space (standard dynamic range, Rec. 709).

19.10 Music and sound design

  • Sources: licensed libraries, operator-owned recordings, and generated music only where the provider terms permit the intended use. Every track is recorded in the Rights & Provenance Ledger before compose (Sections 20.3 and 20.3).
  • A MusicBrief is derived from the script: mood, energy curve, tempo range, duration, sections, instruments to avoid, and vocal or instrumental.
  • Candidates are searched by metadata and fitted to picture: trimmed or looped on bar boundaries and ended on a natural ending. A beat grid is optional for aligning cuts.
  • A SoundCue is created from each Shot.audio_cues entry (Section 16.2): type (effect, ambience, foley), description, offset, duration, asset and gain.
  • The mix keeps separate stems for dialogue, music, effects and ambience. Dialogue has priority, with automatic ducking of music under speech.
  • Loudness is normalised to the target in the channel profile, with a true-peak ceiling. Targets are configuration values to be verified per platform.
  • An AudioMixProfile holds: stem gains, ducking depth and timing, loudness target, peak ceiling and fades.
  • Stems are retained for re-mixing, localisation and repurposing.
  • QC extends the audio row of Section 20.1: music masking speech, abrupt music endings and missing cue assets. An unlicensed track is a hard block.
  • The baseline implementation is deterministic FFmpeg audio processing. Finishing in Resolve is optional.

19.11 Audio clean-up

  • Applies to footage with speech, before the mix of Section 19.10.
  • Steps: noise reduction, hum removal, levelling of speech. Settings are conservative, because over-processing damages the voice more than noise does.
  • A speech-enhancement model may be used through a model adapter; it is a candidate to be verified, and it must respect the privacy class of the asset.
  • The original audio is kept. The cleaned track is a derived asset version, and the review screen can compare the two.
  • QC checks that speech is intelligible and that no processing artefacts were introduced, by measurement and by sampled listening.

19.12 Incremental render and fast preview

If changing one clip re-renders the whole video, the fix-and-review loop is slow and the operator stops fixing. Render work is therefore cached per timeline item.

  • Render unit: each TimelineItem is rendered on its own to an intermediate file with all its picture transforms applied.
  • Cache key: the asset version checksum, in and out points, transforms, output specification and tool versions. An unchanged item is never rendered again.
  • A transition between two items is rendered as its own short segment, keyed by both neighbours.
  • Captions and graphics are composited per segment, so only segments whose overlay changed are re-encoded.
  • Audio is mixed separately from stems and joined at the end; a picture change does not re-mix audio, and an audio change does not re-render picture.
  • The final file is assembled from cached segments. QC always runs on the assembled file.
  • Preview uses the same graph on proxies at low resolution. The target preview time is to be set from measurement.
  • The segment cache is derived data under the retention policy. The intermediate format is chosen from measurement, weighing speed against the limited disk.

20.3 Rights, provenance and content safety

  • Every external or generated asset records its origin, creator or provider, licence or terms, permitted use, attribution requirement, expiry and review status.
  • Assets are classed as owned, licensed, public-domain, user-supplied, generated or unknown. Unknown or restricted rights block publishing unless an exception is documented.
  • Rights and privacy propagate to everything derived from an asset.
  • Identifiable people, voices, likenesses and trademarks need the appropriate permission. People are not identified by the system unless the operator labels them.
  • Authentic footage and illustrative synthetic media are kept distinct, and synthetic content is disclosed where a platform or law requires it.
  • A takedown or complaint is traced through lineage to every render and post that used the asset.
  • High-risk topics — medical, financial, political, crisis, minors, impersonation — are blocked or sent to mandatory review by policy.

20.4 Evaluation and regression

  • A benchmark set of representative scripts, footage and shot briefs is kept with its expected results and the operator's labelled decisions.
  • A change of model, prompt, template or pipeline is run against the benchmark before it becomes the default; a regression on a blocking criterion stops the change.
  • Model-based judgements — matching, candidate quality, whole-video review — are calibrated against the operator's recorded decisions.

20.5 Reducing review load

Pipeline B has up to five human gates and pipeline A up to seven. At several videos a day the operator becomes the bottleneck. The aim is review by exception: the operator sees what the system is unsure about, not everything.

  • Gate policy: each gate in a format template is set to required, confidence-based or off.
  • Confidence-based acceptance: an item is accepted without review only when every must-have passes, the judge score is above a threshold, the margin over the runner-up is above a threshold, and nothing is flagged for rights, privacy or risk. Otherwise it is queued.
  • Graduation: confidence-based acceptance is enabled for a gate only after the operator's recorded decisions agree with the system's first choice at a target rate over an agreed number of decisions (MatchFeedback, 18.2.6). Thresholds start strict.
  • Combined review: one screen walks script, clips and preview together and highlights only the low-confidence items.
  • Batch review across projects, so that similar decisions are taken together.
  • Sampling audit: a share of auto-accepted items is still shown to the operator, to detect drift; a fall in agreement switches the gate back to required.
  • Never automatic: approval of a final render before publishing, unknown rights, high-risk topics, and the policy cases of Section 23.4.
  • Measured by operator minutes per finished minute and by the number of gates touched per video.

26.6 Render and finishing tools

  • A timeline exported for Resolve opens with every clip at the correct in and out points and in the correct order.
  • A hand-off package contains every selected clip, the audio files and the captions, and nothing else.
  • An externally finished video cannot be published until it has been re-imported and has passed QC and Review.
  • When Resolve is closed, a level-2 render request reports unavailable and does not hang.

26.7 Production board

  • A state change in a run appears on the board without a manual refresh.
  • Missing or malformed data degrades one card or panel and never breaks the page.
  • Replay of a finished run reproduces the order in which stages and cards changed.
  • The board performs no write through the API.
  • Every function listed in 22.2.1 is present.

26.8 Required failure tests

  • A provider times out after accepting a job; a callback arrives twice; the worker restarts during generation; a run is cancelled during repair.
  • A licence is invalid, expired or unknown; attribution is missing; a reference image has unclear permission.
  • A generated character changes face or wardrobe; a logo is wrong; a clip flickers; a scene contradicts the script; every candidate fails; the budget is exhausted.
  • A file is corrupted, has an unsupported codec, the wrong duration or aspect ratio, silent audio or a mismatched frame rate.
  • Analysis interrupted by restart, sleep or low disk resumes from the last stage checkpoint without paying again for completed stages.
  • Video with no speech; a single long take with no shot changes; mixed languages; a multi-hour file; a corrupted or variable-frame-rate file.
  • The vision model returns an empty or contradictory description; a summary cites evidence that does not exist.
  • Operator-corrected text survives re-analysis.
  • A script line has no matching footage; several lines compete for the same clip; a caption is wrong and the keyframe check must catch it; an abstract line returns only weak candidates.
  • Word timestamps drift; speakers overlap; a retake has no clear winner.
  • The subject leaves the frame; two subjects compete; sync sources share no common audio.
  • A provider clip limit changes; a seam fails repeatedly; dialogue audio is regenerated after visuals exist.
  • A music licence is expired or unknown; a cue asset is missing; the mix exceeds the peak ceiling.
  • The volume holding originals is disconnected in the middle of a render.
  • A file is moved or renamed on its volume; a file is modified so that its checksum changes.
  • The narration is regenerated after the timeline was approved.
  • A caption line contains characters the font lacks; a line is too long to fit any rule.
  • An HDR source has missing or wrong colour metadata.
  • Stabilisation and reframing together would crop away the subject.
  • The enhancement provider is unavailable or returns a clip with a different duration.
  • The disk fills while proxies are being created.
