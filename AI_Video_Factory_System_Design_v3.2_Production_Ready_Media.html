1. Executive Summary

AI Video Factory is a personal AI-assisted video production system that automates as much of the workflow as practical: research, scripting, footage discovery, assembly, preview, quality checks, approval, publishing and performance analysis. The initial target is approximately 1–10 short videos per day, subject to video complexity, model latency, render time and hardware capacity.

1.1 Target architecture

Hermes Agent is the control plane and primary user interaction point. A separately managed Video Factory Platform provides job orchestration, asset metadata, events, review and search APIs. OpenMontage Backlot is reused as a production-specific board, while FFmpeg, DaVinci Resolve and AI services perform specialist tasks through adapters.

1.2 Design principles

  • Hermes-first: users issue requests and monitor outcomes through Hermes.
  • Reuse before rebuild: reuse Backlot UI and existing Hermes tools wherever practical.
  • API-first integration: normalize engine operations behind explicit adapters.
  • Local-first: keep media and metadata local unless cloud services provide a clear benefit.
  • Single source of truth: job and asset state live outside individual engine UIs.
  • Human-in-the-loop: preview and approval gates precede public publishing.
  • Recoverable automation: state, retries, timeouts, idempotency and logs are first-class.
  • Replaceable engines: new tools should be addable without rewriting the platform.
  • Progressive delivery: prove one end-to-end workflow before broadening scope.

7. Semantic Video Library

7.1 Search experience

Users should be able to search by filename, tags, transcript, scene description, objects, actions and semantic similarity. Results should identify the source asset and, where possible, the relevant timestamp or clip range.

7.2 Indexing pipeline

INGEST -> FFprobe metadata -> thumbnails / selected keyframes -> transcription with timestamps -> visual analysis -> optional embeddings -> metadata + full-text + optional vector index -> ranked search results

 

7.3 Progressive implementation

  • Start with file discovery, FFprobe metadata and thumbnails.
  • Add transcription and timestamped text search.
  • Add visual analysis for selected or high-value assets.
  • Add embeddings and vector search after retrieval quality can be evaluated.
  • Invalidate or refresh analysis when the underlying asset checksum changes.

9. Engine Adapters

9.1 FFmpeg / FFprobe

  • Inspect codecs, streams, duration, resolution and frame rate.
  • Create proxies, thumbnails and previews.
  • Trim/concatenate media, normalize formats, mix audio and process subtitles.
  • Validate output and capture command, version, exit code and logs.

9.2 OpenMontage

Build an adapter only after confirming the supported CLI/API and project layout. The adapter should normalize status and register outputs; it should not assume every UI operation is exposed as an API.

9.3 DaVinci Resolve

First run a proof of concept against the installed version and edition: detect Resolve, verify scripting/API access, import media, create/update a simple timeline, render, retrieve status and handle failure. The final adapter scope must follow verified capabilities rather than assumptions.

9.4 AI provider adapters

Normalize text generation, research, image generation, speech generation, transcription, video analysis and embeddings. Apply timeouts, usage limits, credential isolation, cost controls and model/version metadata.

11. API and Integration Contracts

11.1 Contract rules

  • Use explicit schemas and stable IDs instead of arbitrary file paths wherever possible.
  • Long-running operations return a job_id; clients poll or subscribe to status.
  • Use idempotency keys for operations that can create side effects.
  • Normalize errors into stable codes and readable messages.
  • Register verified outputs in the Asset Registry.

13. Security, Reliability and Operations

13.1 Execution safety

  • Restrict shell tools to approved operations and directories.
  • Separate read-only operations from operations with side effects.
  • Protect final renders from accidental overwrite or deletion.
  • Require approval for public publishing and destructive actions.

13.2 Secrets and credentials

  • Store API keys and publishing tokens in an appropriate secrets mechanism.
  • Do not put secrets in prompts, logs, manifests or source control.
  • Limit each adapter to the credentials it needs.

13.3 Recovery and backup

  • Persist state transitions before and after important operations.
  • Set timeouts and retry policies by operation type.
  • Distinguish transient failures from configuration errors.
  • On restart, reconcile running jobs against engine state and existing outputs.
  • Back up metadata, manifests, scripts and important configuration; define a separate policy for large media files.

13.4 Publishing safeguards

Default to preview and approval before public publication. Verify the target account, privacy settings, metadata and final file. Store platform identifiers and report success only when confirmed by the platform.

16. Testing and Acceptance Criteria

16.1 Integration tests

  • Hermes can invoke the Video Factory plugin.
  • A tool call creates a job and returns a valid job_id.
  • Job Registry records normalized status transitions.
  • An adapter starts an engine and captures output/logs.
  • Verified output is registered in the Asset Registry.
  • Dashboard status matches canonical platform state.
  • Engine failures map to stable error codes.

16.2 Reliability tests

  • Stop the service while a job is running and verify reconciliation after restart.
  • Simulate timeout, missing source file and invalid output.
  • Retry a failed job and verify no unintended duplicate side effects.
  • Confirm history of earlier attempts is preserved.

16.3 Media quality checks

  • Verify duration, resolution, codec and required streams.
  • Verify subtitle presence and audio/video synchronization.
  • Confirm output is readable by a media probe/player.
  • Validate aspect ratio and other project-specific requirements.

16.4 End-to-end acceptance

  1. User submits a request through Hermes.
  2. System creates a project/job and executes the configured workflow.
  3. Job state and logs are queryable.
  4. A preview is produced and reviewable.
  5. Final render is validated and registered.
  6. Project, assets and history remain linked.
  7. If published, the platform's confirmation and resulting identifier are stored.

20. Final Recommendation

The recommended architecture combines Hermes Agent as the control plane, a small Video Factory Platform for durable state and integration, OpenMontage Backlot as the reusable production board, and adapters for media and AI engines. Avoid building a large dashboard or integrating many MCP servers before the first workflow is proven.

Recommended order:

  1. Inventory actual tools and validate the environment.
  2. Prove Hermes → Video Factory plugin → Job Registry → FFmpeg/OpenMontage → preview.
  3. Stabilize Job Registry, Asset Registry and normalized status.
  4. Run the Backlot embedding POC in Hermes Dashboard.
  5. Complete preview, review and revision handling.
  6. Add semantic footage search.
  7. Validate Resolve integration.
  8. Add publishing and analytics last.

22. Content Intelligence and Research Memory

22.1 Responsibilities

  • Accept a human brief or proactively propose topics within explicitly configured channel, audience, language, niche, frequency and budget boundaries.
  • Gather source-backed evidence: source URL/title, publisher, publication date where available, retrieval timestamp, extracted claim, supporting passage and confidence.
  • Produce an idea backlog with a transparent scorecard: audience fit, novelty, evidence strength, production feasibility, channel fit, estimated cost, rights/safety risk and freshness.
  • Maintain content pillars, series plans, editorial calendar, planned-versus-published state and topic saturation checks.
  • Separate verified facts, hypotheses, opinion, and creative invention. Require citations for factual claims where relevant.
  • Store reusable research briefs and connect each brief to scripts, assets, published videos and measured outcomes.

22.2 Suggested research workflow

  1. Define objective and constraints: audience, platform, language, target duration, tone, budget, deadlines and forbidden claims.
  2. Discover candidate topics and primary/credible sources.
  3. Cross-check material claims, publication dates and contradictory evidence.
  4. Generate multiple angles and hook options; score them against the configured rubric.
  5. Run a critique pass for originality, evidence, rights, sensitivity and production feasibility.
  6. Human approval is required for new channels, high-risk topics or policy-defined cases; approved ideas become versioned production briefs.

23. Story Intelligence and Creative Planning

Treat the script as structured data, not only a text blob. This enables continuity checks, selective regeneration and deterministic editing.

  • Represent a production brief as scenes/shots with IDs, intent, duration target, visual description, dialogue/voice-over, on-screen text, sound cues, source assets and generation instructions.
  • Link each shot to the storyboard frame, generated media, timeline segment and QC result.
  • Version script, storyboard and edit decision list; maintain a change log and dependency map.
  • Support alternate hooks, endings and cut lengths without duplicating the entire project.
  • Run continuity checks for recurring people/characters, wardrobe, location, props, visual style, voice identity and chronology.
  • Use a human creative review step for story quality where model scores alone are insufficient.

24. Workflow Orchestration and Durable Execution

24.1 Design rule

Hermes is the agent/control interface. Video Factory Service is the authoritative owner of business job state. The service must not require an uninterrupted agent session to finish or recover a production job.

24.2 Required controls

  • Persistent job store and explicit state machine, with state transition validation.
  • Queue and concurrency limits by job type, model provider and local hardware capability.
  • Dependency graph and checkpoints between research, script, asset generation, editing, QC, approval and publishing.
  • Bounded retries with exponential backoff where appropriate, timeout, cancellation, dead-letter/error state and manual resume.
  • Idempotency keys for external side effects; distinguish retry-safe operations from operations requiring reconciliation.
  • Persist input parameters, artifact references, provider/model versions, costs, logs and outputs for each attempt.
  • Support process restarts, Mac sleep/wake, interrupted render, network outage, rate limits and partial outputs.

28. Performance Intelligence and Learning Loop

28.1 Data model

  • Store periodic metric snapshots rather than overwriting values: views, impressions, watch time, average view duration, retention points, completion, engagement and CTR where the platform provides them.

  • Separate correlation from causation. Record audience size, distribution timing, promotion and other confounders where known.
  • Build comparisons by channel and content format; avoid comparing raw numbers across materially different audiences or platforms.
  • Feed validated findings back to idea scoring and creative profiles with provenance and confidence.

28.2 Experiment governance

  • Define a hypothesis, primary metric, guardrail metric, variants, duration and decision rule before an experiment.
  • Change a limited number of variables per test where possible.
  • Do not declare a winner from insufficient sample size or a short-lived fluctuation.
  • Require approval before automatically changing brand policy, factual standards, safety gates or publishing permissions.
  • Maintain a learning ledger: hypothesis, evidence, conclusion, confidence, applicability and expiry/revalidation date.

29.2 Rights and provenance

  • For every external/generated asset, record origin, creator/provider, license/terms reference, acquisition date, permitted use, attribution requirements, expiry and review status.

  • Preserve sources and evidence for factual claims; keep disclosure metadata for synthetic media when required by law or platform policy.

43. Distribution and growth loop

  1. Define a channel profile: target audience, objective, duration range, aspect ratio, caption rules, safe areas, cadence, allowed topics, restricted topics and metric definitions.
  2. Opportunity Radar gathers source-backed candidates and scores audience fit, freshness, demand signals, differentiation, evidence quality, production cost, rights risk and channel fit.
  3. Select one primary hypothesis and one primary outcome metric. Avoid changing hook, duration, title and CTA simultaneously if the intent is to learn which variable caused a difference.
  4. Produce a small bounded variant set; use low-cost previews/animatics before expensive renders when the story is uncertain.
  5. Run automated QC: file integrity, codec/resolution/frame rate, duration, loudness/peak, subtitle timing, safe-area text, blank/frozen frames, rights/provenance, claims and policy risk.
  6. Publish only through an approved channel profile and policy gate. Persist external IDs and reconcile ambiguous outcomes.
  7. Collect metrics at defined windows, e.g. early, 24-hour and 7-day where platform APIs support it. Record unavailable metrics rather than silently treating them as zero.
  8. Update the Content Brain with observations and confidence. Recommend experiments; do not automatically conclude causality from a single post.

North-star metric should be chosen per business model. For an audience-growth channel, use a composite such as qualified watch time or retention plus follows/subscriptions per 1,000 views, with cost per approved/published video as an efficiency constraint. Views alone are a weak optimization target.

47. Risks and anti-patterns

  • Do not optimize only for views or viral potential; include audience fit, retention, conversion and content integrity.
  • Do not build a custom scheduler before proving one official publishing path.
  • Do not add vector/graph databases before a retrieval benchmark demonstrates a material gain over full-text search.
  • Do not let multiple agents mutate the same project state concurrently without a single writer or optimistic concurrency control.
  • Do not trust AI QC as a substitute for deterministic media validation, rights checks or platform-policy gates.
  • Do not treat social platform metrics as directly comparable without normalizing definitions and measurement windows.
  • Do not infer causal lift from before/after comparisons without accounting for topic, timing, audience and distribution differences.
  • Do not allow high autonomy to mean unrestricted spending, account actions, or public publishing.

61. Asset Intelligence & Generation Engine

Introduce a first-class domain service rather than a single all-purpose agent. It is responsible for planning asset acquisition, routing retrieval/generation tasks, scoring candidate assets, validating rights, coordinating quality checks and returning approved asset IDs to the production workflow.

61.1 Logical components

  • Asset Planner: converts each scene/shot brief into required subjects, action, setting, shot size, camera movement, duration, aspect ratio, style constraints, factual constraints and must-not-change invariants.

  • Media Generation Router: selects image/video generation providers by modality, quality evidence, reference support, temporal consistency, latency, cost, policy and availability.
  • Reference & Continuity Manager: stores approved character sheets, location references, product references, visual style guides and scene continuity constraints.

  • Asset Repair Loop: identifies defect type, chooses targeted regeneration/editing, preserves valid constraints and caps attempts and cost.

62. End-to-End Workflow and Durable State

  1. Ingest approved script and compile it into SceneSpec and ShotSpec records.
  2. Asset Planner generates an AssetPlan with retrieval/generation alternatives, expected quality, rights requirements and cost ceiling.
  3. Discovery and generation adapters create candidate assets asynchronously; all external jobs use idempotency keys and persisted provider job IDs where available.
  4. Normalize candidate metadata and run technical validation, semantic/script alignment, visual quality, continuity, duplicate and rights checks.
  5. If a repairable defect is detected, create a bounded RepairPlan and regenerate only the affected asset or shot; retain lineage to the failed version.
  6. If mandatory gates pass, mark an immutable asset version ApprovedForEdit and make it available to the renderer. If not, quarantine it or route to human review.
  7. Render a preview/animatic, inspect timeline-level continuity and pacing, then perform final media and audio validation.
  8. Publish only after the separate publishing policy gates pass; retain the source assets and provenance for audit and later revisions.

Workflow state must live in Video Factory Service, not solely in agent conversation history or the production board. Required states include Planned, Searching, Generating, CandidateReady, QAInProgress, RepairQueued, HumanReview, ApprovedForEdit, Rejected, Failed, Cancelled and Archived. State transitions must be auditable and idempotent.

66. Repair Loop, Fallbacks and Cost Controls

  • Use defect-specific repairs: wrong object → revise object constraints; identity drift → strengthen references and invariant checks; temporal flicker → try a different model/settings or split the shot; wrong factual detail → retrieve verified footage.
  • Generate a small candidate set first; expand only if no candidate passes. Avoid generating many variants without an evaluation plan.
  • Cap retries per shot, cost per shot, total job cost, parallel provider calls and wall-clock duration. Require explicit policy approval for budget increases.
  • Use circuit breakers and provider health tracking. Persist task status before and after external calls; reconcile orphaned provider jobs after restart.
  • Never relax rights, factuality, consent or critical quality gates just to complete a job. If no valid candidate exists, mark blocked and offer a safe alternative.

67. Rights, Safety and Disclosure

  • Use only providers and sources whose terms permit the intended use; record license evidence, attribution and restrictions at asset-version level.
  • Obtain required permissions for identifiable people, voices, likenesses, trademarks and user-supplied material; apply additional controls to sensitive or misleading depictions.
  • For factual reporting, preserve source references and distinguish authentic footage from illustrative synthetic media. Apply disclosure/watermarking when required by platform policy, law or editorial policy.
  • Run copyright/duplicate similarity checks where appropriate, but treat them as signals rather than legal determinations.
  • Keep a human review route for high-risk categories, unresolved rights, realistic depictions that could mislead, and any low-confidence QA result.

70. Architecture Decision Record — Level 4 Media

Decision

Adopt Production-Ready Photorealistic Media as an end-to-end release standard enforced by policy and automated QA, with category-specific thresholds and human calibration. Use retrieval-first when authenticity, exact identity, factual precision or rights clarity matter; use generation-first when fictional or illustrative content is appropriate; support hybrid workflows.

Consequences

  • Quality is a pipeline property and cannot be guaranteed by selecting a single model.
  • Asset and lineage schemas, provider adapters, evaluation sets and QA gates become first-class components.
  • Initial build is intentionally narrow: one retrieval source, one image-generation provider, one video-generation path, one QA profile and FFmpeg render integration; expand based on measured results.
  • Autonomy increases only after acceptance metrics are demonstrated. High-risk or unresolved cases remain human-gated.
  • All numeric quality thresholds are provisional until validated against representative output and reviewer calibration.

Final design position

AI Video Factory v3.2 treats the media pipeline as a controlled production system: discover or generate → evaluate → repair → release → render → audit. The goal is repeatable production readiness for defined video categories, not an unrealistic promise that every AI-generated frame will be indistinguishable from real footage.
