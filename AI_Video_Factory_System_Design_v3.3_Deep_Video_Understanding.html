1. Executive Summary

AI Video Factory is a personal AI-assisted video production system that automates as much of the workflow as practical: research, scripting, footage discovery, assembly, preview, quality checks, approval, publishing and performance analysis. The initial target is approximately 1–10 short videos per day, subject to video complexity, model latency, render time and hardware capacity.

1.1 Target architecture

The NEXORA service is the control point: it owns job orchestration, asset metadata, events, review and search APIs, and is operated through its own Web UI. FFmpeg, DaVinci Resolve and AI services perform specialist tasks through adapters. The production board is a screen of the Web UI (Section 109). The layer model is defined in Section 84.

1.2 Design principles

  • Reuse before rebuild: reuse proven tools and designs wherever practical.
  • API-first integration: normalize engine operations behind explicit adapters.
  • Local-first: keep media and metadata local unless cloud services provide a clear benefit.
  • Single source of truth: job and asset state live outside individual engine UIs.
  • Human-in-the-loop: preview and approval gates precede public publishing.
  • Recoverable automation: state, retries, timeouts, idempotency and logs are first-class.
  • Replaceable engines: new tools should be addable without rewriting the platform.
  • Progressive delivery: prove one end-to-end workflow before broadening scope.

2. System Context and External Systems

2.1 Primary user journey

The user asks the system to research a topic, draft a script, locate relevant footage, assemble a video, create a preview, review the result and—after approval—publish it. The service runs each stage, giving reasoning steps to bounded agents and media steps to the relevant engines, and persists the workflow state.

6. Video Factory Platform Services

6.1 Job Registry

The Job Registry is the canonical source of execution state across engines. Its records are Run, Stage and Attempt, defined in Section 89.

 

6.2 Job lifecycle rules

 

  • A retry must not create duplicate publishing side effects or unintended duplicate outputs.
  • Retain prior attempts; do not overwrite history with the latest attempt.
  • After restart, reconcile in-flight jobs with engine state and existing output files.
  • Mark success only after validating the expected output.

7. Semantic Video Library

7.1 Search experience

Users should be able to search by filename, tags, transcript, scene description, objects, actions and semantic similarity. Results should identify the source asset and, where possible, the relevant timestamp or clip range.

7.2 Indexing pipeline

INGEST -> FFprobe metadata -> thumbnails / selected keyframes -> transcription with timestamps -> visual analysis -> optional embeddings -> metadata + full-text + optional vector index -> ranked search results

 

7.3 Progressive implementation

  • Start with file discovery, FFprobe metadata and thumbnails.
  • Add transcription and timestamped text search.
  • Add visual analysis for selected or high-value assets.
  • Add embeddings and vector search after retrieval quality can be evaluated.
  • Invalidate or refresh analysis when the underlying asset checksum changes.

9. Engine Adapters

9.1 FFmpeg / FFprobe

  • Inspect codecs, streams, duration, resolution and frame rate.
  • Create proxies, thumbnails and previews.
  • Trim/concatenate media, normalize formats, mix audio and process subtitles.
  • Validate output and capture command, version, exit code and logs.

9.2 OpenMontage

Build an adapter only after confirming the supported CLI/API and project layout. The adapter should normalize status and register outputs; it should not assume every UI operation is exposed as an API.

9.3 DaVinci Resolve

First run a proof of concept against the installed version and edition: detect Resolve, verify scripting/API access, import media, create/update a simple timeline, render, retrieve status and handle failure. The final adapter scope must follow verified capabilities rather than assumptions.

9.4 AI provider adapters

Normalize text generation, research, image generation, speech generation, transcription, video analysis and embeddings. Apply timeouts, usage limits, credential isolation, cost controls and model/version metadata.

11. API and Integration Contracts

11.1 Contract rules

  • Use explicit schemas and stable IDs instead of arbitrary file paths wherever possible.
  • Long-running operations return a job_id; clients poll or subscribe to status.
  • Use idempotency keys for operations that can create side effects.
  • Normalize errors into stable codes and readable messages.
  • Register verified outputs in the Asset Registry.

13. Security, Reliability and Operations

13.1 Execution safety

  • Restrict shell tools to approved operations and directories.
  • Separate read-only operations from operations with side effects.
  • Protect final renders from accidental overwrite or deletion.
  • Require approval for public publishing and destructive actions.

13.2 Secrets and credentials

  • Store API keys and publishing tokens in an appropriate secrets mechanism.
  • Do not put secrets in prompts, logs, manifests or source control.
  • Limit each adapter to the credentials it needs.

13.3 Recovery and backup

  • Persist state transitions before and after important operations.
  • Set timeouts and retry policies by operation type.
  • Distinguish transient failures from configuration errors.
  • On restart, reconcile running jobs against engine state and existing outputs.
  • Back up metadata, manifests, scripts and important configuration; define a separate policy for large media files.

13.4 Publishing safeguards

Default to preview and approval before public publication. Verify the target account, privacy settings, metadata and final file. Store platform identifiers and report success only when confirmed by the platform.

16. Testing and Acceptance Criteria

16.1 Integration tests

  • A tool call creates a job and returns a valid job_id.
  • Job Registry records normalized status transitions.
  • An adapter starts an engine and captures output/logs.
  • Verified output is registered in the Asset Registry.
  • Dashboard status matches canonical platform state.
  • Engine failures map to stable error codes.

16.2 Reliability tests

  • Stop the service while a job is running and verify reconciliation after restart.
  • Simulate timeout, missing source file and invalid output.
  • Retry a failed job and verify no unintended duplicate side effects.
  • Confirm history of earlier attempts is preserved.

16.3 Media quality checks

  • Verify duration, resolution, codec and required streams.
  • Verify subtitle presence and audio/video synchronization.
  • Confirm output is readable by a media probe/player.
  • Validate aspect ratio and other project-specific requirements.

16.4 End-to-end acceptance

  1. User submits a request through the Web UI or API.
  2. System creates a project/job and executes the configured workflow.
  3. Job state and logs are queryable.
  4. A preview is produced and reviewable.
  5. Final render is validated and registered.
  6. Project, assets and history remain linked.
  7. If published, the platform's confirmation and resulting identifier are stored.

22. Content Intelligence and Research Memory

22.1 Responsibilities

  • Accept a human brief or proactively propose topics within explicitly configured channel, audience, language, niche, frequency and budget boundaries.
  • Gather source-backed evidence: source URL/title, publisher, publication date where available, retrieval timestamp, extracted claim, supporting passage and confidence.
  • Produce an idea backlog with a transparent scorecard: audience fit, novelty, evidence strength, production feasibility, channel fit, estimated cost, rights/safety risk and freshness.
  • Maintain content pillars, series plans, editorial calendar, planned-versus-published state and topic saturation checks.
  • Separate verified facts, hypotheses, opinion, and creative invention. Require citations for factual claims where relevant.
  • Store reusable research briefs and connect each brief to scripts, assets, published videos and measured outcomes.

22.2 Suggested research workflow

  1. Define objective and constraints: audience, platform, language, target duration, tone, budget, deadlines and forbidden claims.
  2. Discover candidate topics and primary/credible sources.
  3. Cross-check material claims, publication dates and contradictory evidence.
  4. Generate multiple angles and hook options; score them against the configured rubric.
  5. Run a critique pass for originality, evidence, rights, sensitivity and production feasibility.
  6. Human approval is required for new channels, high-risk topics or policy-defined cases; approved ideas become versioned production briefs.

23. Story Intelligence and Creative Planning

Treat the script as structured data, not only a text blob. This enables continuity checks, selective regeneration and deterministic editing.

  • Represent a production brief as scenes/shots with IDs, intent, duration target, visual description, dialogue/voice-over, on-screen text, sound cues, source assets and generation instructions.
  • Link each shot to the storyboard frame, generated media, timeline segment and QC result.
  • Version script, storyboard and edit decision list; maintain a change log and dependency map.
  • Support alternate hooks, endings and cut lengths without duplicating the entire project.
  • Run continuity checks for recurring people/characters, wardrobe, location, props, visual style, voice identity and chronology.
  • Use a human creative review step for story quality where model scores alone are insufficient.

24. Workflow Orchestration and Durable Execution

24.1 Design rule

Video Factory Service is the authoritative owner of business job state. The service must not require an uninterrupted agent session to finish or recover a production job.

24.2 Required controls

  • Persistent job store and explicit state machine, with state transition validation.
  • Queue and concurrency limits by job type, model provider and local hardware capability.
  • Dependency graph and checkpoints between research, script, asset generation, editing, QC, approval and publishing.
  • Bounded retries with exponential backoff where appropriate, timeout, cancellation, dead-letter/error state and manual resume.
  • Idempotency keys for external side effects; distinguish retry-safe operations from operations requiring reconciliation.
  • Persist input parameters, artifact references, provider/model versions, costs, logs and outputs for each attempt.
  • Support process restarts, Mac sleep/wake, interrupted render, network outage, rate limits and partial outputs.
  • Use event notifications/webhooks or SSE for UI updates; event delivery must not be the only persistence mechanism.

24.4 Recovery contract

On restart, reconcile queued/running jobs against process leases, inspect whether external side effects occurred, verify artifact checksums and resume from the last safe checkpoint. Never assume that a timed-out request had no effect.

25. Unified Media Asset Intelligence

25.1 Asset registry responsibilities

  • Assign stable asset_id and store media type, duration, dimensions, codec, file size, checksum, source, rights status, project, tags, language, creation time and storage location.
  • Track lineage: source media → transcript/derivatives → scene/shot → edit → render → published post.
  • Store thumbnails/contact sheets, transcript segments with timestamps, scene boundaries and optional object/action/person descriptors where legally and technically appropriate.
  • Index first by reliable metadata and full-text transcript. Add vector retrieval only after an evaluation set proves it improves discovery.
  • Detect duplicates using checksum and optional perceptual similarity; do not delete automatically without retention policy.
  • Support lifecycle tiers, storage quotas, retention, backup and explicit deletion behavior.

27. Distribution and Channel Operations

  • Represent each social channel/account as a configured destination with explicit scopes, credential reference, default format, brand profile and publication policy.
  • Prepare platform-specific packages: render, title, description, hashtags, thumbnail, captions, disclosures and language variants.
  • Support scheduled, draft, manual publish and approved auto-publish modes.
  • Store external post ID, URL, destination, status, timestamps, API response summary and reconciliation state.
  • Use provider-specific adapters; validate current API availability, access review, quota, media requirements and commercial/personal account constraints before implementation.
  • Handle rate limits, upload resumability where supported, expired credentials, moderation rejection, duplicate-post prevention and post-publication edits.
  • Keep publishing as a distinct workflow from rendering; a rendered video is not automatically approved to publish.

28. Performance Intelligence and Learning Loop

28.1 Data model

  • Store periodic metric snapshots rather than overwriting values: views, impressions, watch time, average view duration, retention points, completion, engagement and CTR where the platform provides them.
  • Link each post and metric snapshot to the exact render, script version, hook, thumbnail, topic, duration, channel and publication context.
  • Separate correlation from causation. Record audience size, distribution timing, promotion and other confounders where known.
  • Build comparisons by channel and content format; avoid comparing raw numbers across materially different audiences or platforms.
  • Feed validated findings back to idea scoring and creative profiles with provenance and confidence.

28.2 Experiment governance

  • Define a hypothesis, primary metric, guardrail metric, variants, duration and decision rule before an experiment.
  • Change a limited number of variables per test where possible.
  • Do not declare a winner from insufficient sample size or a short-lived fluctuation.
  • Require approval before automatically changing brand policy, factual standards, safety gates or publishing permissions.
  • Maintain a learning ledger: hypothesis, evidence, conclusion, confidence, applicability and expiry/revalidation date.

29. Brand Memory, Provenance and Content Safety

29.1 Brand/creative profiles

Maintain versioned profiles per channel or series: audience, voice, pacing, visual references, palette, typography, logo rules, subtitle style, intro/outro, preferred transitions, narration style, pronunciation dictionary, banned phrases and examples of accepted/rejected work.

29.2 Rights and provenance

  • For every external/generated asset, record origin, creator/provider, license/terms reference, acquisition date, permitted use, attribution requirements, expiry and review status.
  • Distinguish owned, licensed, public-domain, user-supplied, generated and unknown-rights assets.
  • Unknown or restricted rights must trigger a publish block or explicit documented exception.
  • Preserve sources and evidence for factual claims; keep disclosure metadata for synthetic media when required by law or platform policy.
  • Provide a takedown/complaint workflow that identifies affected renders and posts through lineage links.

29.3 Safety boundaries

  • Treat prompts, source media, transcripts and downloaded files as untrusted input.
  • Do not allow source content to override system policy or directly trigger shell commands, credential access or publishing.
  • Use least-privilege tool permissions, allow-listed operations, path validation, process isolation and explicit approval for destructive/high-impact actions.
  • Require human approval for high-risk topics, uncertain rights, sensitive depictions, new destinations or policy exceptions.

31. FinOps, Observability and Operational Security

31.1 FinOps

  • Tag every provider call and render with project_id, job_id, stage, model/provider, usage units, duration and estimated/actual cost.
  • Report cost per generated video, cost per QC-passed video and cost per published video.
  • Enforce project/day/month budgets, per-job caps and alert thresholds.
  • Use model routing by task risk and quality requirement; cheap models may draft, while critical checks use stronger models or human review.
  • Prevent unbounded retries and recursive agent loops; expose a kill switch for queued work.

31.2 Observability

  • Structured logs, metrics and traces with correlation IDs across the Web UI, Video Factory Service, adapters and provider calls.
  • Dashboard for queue depth, stage latency, success/failure rates, retry counts, cost, disk use, CPU/GPU/memory and unresolved reviews.
  • Redact secrets and sensitive content from logs; define retention and access policy.

43. Distribution and growth loop

  1. Define a channel profile: target audience, objective, duration range, aspect ratio, caption rules, safe areas, cadence, allowed topics, restricted topics and metric definitions.
  2. Opportunity Radar gathers source-backed candidates and scores audience fit, freshness, demand signals, differentiation, evidence quality, production cost, rights risk and channel fit.
  3. Select one primary hypothesis and one primary outcome metric. Avoid changing hook, duration, title and CTA simultaneously if the intent is to learn which variable caused a difference.
  4. Produce a small bounded variant set; use low-cost previews/animatics before expensive renders when the story is uncertain.
  5. Run automated QC: file integrity, codec/resolution/frame rate, duration, loudness/peak, subtitle timing, safe-area text, blank/frozen frames, rights/provenance, claims and policy risk.
  6. Publish only through an approved channel profile and policy gate. Persist external IDs and reconcile ambiguous outcomes.
  7. Collect metrics at defined windows, e.g. early, 24-hour and 7-day where platform APIs support it. Record unavailable metrics rather than silently treating them as zero.
  8. Update the Content Brain with observations and confidence. Recommend experiments; do not automatically conclude causality from a single post.

North-star metric should be chosen per business model. For an audience-growth channel, use a composite such as qualified watch time or retention plus follows/subscriptions per 1,000 views, with cost per approved/published video as an efficiency constraint. Views alone are a weak optimization target.

47. Risks and anti-patterns

  • Do not optimize only for views or viral potential; include audience fit, retention, conversion and content integrity.
  • Do not build a custom scheduler before proving one official publishing path.
  • Do not add vector/graph databases before a retrieval benchmark demonstrates a material gain over full-text search.
  • Do not let multiple agents mutate the same project state concurrently without a single writer or optimistic concurrency control.
  • Do not trust AI QC as a substitute for deterministic media validation, rights checks or platform-policy gates.
  • Do not treat social platform metrics as directly comparable without normalizing definitions and measurement windows.
  • Do not infer causal lift from before/after comparisons without accounting for topic, timing, audience and distribution differences.
  • Do not allow high autonomy to mean unrestricted spending, account actions, or public publishing.

58. Updated build order for a solo developer

  1. Ship the smallest vertical slice: one channel, one format, durable job, approval, publish ledger, reconciliation and metric sync.
  2. Add Content Digital Thread, variant registry and a baseline performance dashboard before advanced AI intelligence.
  3. Build Creative Simulation and semantic edit-plan validation next if revision time is a bottleneck.
  4. Build Opportunity Radar and Content Memory once there is a reliable source registry and at least an initial corpus of posts/results.
  5. Expand to more channels only after the first adapter passes failure, quota, authentication and duplicate-publication tests.
  6. Consider P2 causal and predictive features only when enough comparable observations exist; do not fabricate confidence from small samples.

A single developer should prioritize end-to-end learning speed over the number of features. Every new capability must reduce a measured bottleneck or improve a chosen growth metric; otherwise defer it.

61. Asset Intelligence & Generation Engine

Introduce a first-class domain service rather than a single all-purpose agent. It is responsible for planning asset acquisition, routing retrieval/generation tasks, scoring candidate assets, validating rights, coordinating quality checks and returning approved asset IDs to the production workflow.

61.1 Logical components

  • Asset Planner: converts each scene/shot brief into required subjects, action, setting, shot size, camera movement, duration, aspect ratio, style constraints, factual constraints and must-not-change invariants.

  • Media Generation Router: selects image/video generation providers by modality, quality evidence, reference support, temporal consistency, latency, cost, policy and availability.

  • Asset Repair Loop: identifies defect type, chooses targeted regeneration/editing, preserves valid constraints and caps attempts and cost.

62. End-to-End Workflow and Durable State

  1. Ingest approved script and compile it into SceneSpec and ShotSpec records.
  2. Asset Planner generates an AssetPlan with retrieval/generation alternatives, expected quality, rights requirements and cost ceiling.
  3. Discovery and generation adapters create candidate assets asynchronously; all external jobs use idempotency keys and persisted provider job IDs where available.
  4. Normalize candidate metadata and run technical validation, semantic/script alignment, visual quality, continuity, duplicate and rights checks.
  5. If a repairable defect is detected, create a bounded RepairPlan and regenerate only the affected asset or shot; retain lineage to the failed version.
  6. If mandatory gates pass, mark an immutable asset version ApprovedForEdit and make it available to the renderer. If not, quarantine it or route to human review.
  7. Render a preview/animatic, inspect timeline-level continuity and pacing, then perform final media and audio validation.
  8. Publish only after the separate publishing policy gates pass; retain the source assets and provenance for audit and later revisions.

Workflow state must live in Video Factory Service, not solely in agent conversation history or the production board. States follow the model of Section 89: sourcing progress is carried by stage states, and each asset version has its own lifecycle (89.6). State transitions must be auditable and idempotent.

66. Repair Loop, Fallbacks and Cost Controls

  • Use defect-specific repairs: wrong object → revise object constraints; identity drift → strengthen references and invariant checks; temporal flicker → try a different model/settings or split the shot; wrong factual detail → retrieve verified footage.
  • Generate a small candidate set first; expand only if no candidate passes. Avoid generating many variants without an evaluation plan.
  • Cap retries per shot, cost per shot, total job cost, parallel provider calls and wall-clock duration. Require explicit policy approval for budget increases.
  • Use circuit breakers and provider health tracking. Persist task status before and after external calls; reconcile orphaned provider jobs after restart.
  • Never relax rights, factuality, consent or critical quality gates just to complete a job. If no valid candidate exists, mark blocked and offer a safe alternative.

67. Rights, Safety and Disclosure

  • Use only providers and sources whose terms permit the intended use; record license evidence, attribution and restrictions at asset-version level.
  • Obtain required permissions for identifiable people, voices, likenesses, trademarks and user-supplied material; apply additional controls to sensitive or misleading depictions.
  • For factual reporting, preserve source references and distinguish authentic footage from illustrative synthetic media. Apply disclosure/watermarking when required by platform policy, law or editorial policy.
  • Run copyright/duplicate similarity checks where appropriate, but treat them as signals rather than legal determinations.
  • Keep a human review route for high-risk categories, unresolved rights, realistic depictions that could mislead, and any low-confidence QA result.

70. Architecture Decision Record — Level 4 Media

Decision

Adopt Production-Ready Photorealistic Media as an end-to-end release standard enforced by policy and automated QA, with category-specific thresholds and human calibration. Use retrieval-first when authenticity, exact identity, factual precision or rights clarity matter; use generation-first when fictional or illustrative content is appropriate; support hybrid workflows.

Consequences

  • Quality is a pipeline property and cannot be guaranteed by selecting a single model.
  • Asset and lineage schemas, provider adapters, evaluation sets and QA gates become first-class components.
  • Initial build is intentionally narrow: one retrieval source, one image-generation provider, one video-generation path, one QA profile and FFmpeg render integration; expand based on measured results.
  • Autonomy increases only after acceptance metrics are demonstrated. High-risk or unresolved cases remain human-gated.
  • All numeric quality thresholds are provisional until validated against representative output and reviewer calibration.

Final design position

AI Video Factory v3.2 treats the media pipeline as a controlled production system: discover or generate → evaluate → repair → release → render → audit. The goal is repeatable production readiness for defined video categories, not an unrealistic promise that every AI-generated frame will be indistinguishable from real footage.

72.3 Frame coverage policy

Requirement: every frame of a video must be resolvable to a description. Coverage is therefore defined as follows: every timestamp maps to exactly one FrameObservation whose valid range contains it. Describing literally every frame with a vision model is supported, but it is rarely justified — consecutive frames are nearly identical, and a 10-minute clip at 30 frames per second contains 18,000 frames.

  • Cheap signals are computed on every decoded frame of the proxy: scene-change score, motion magnitude, blur and exposure, perceptual hash. These need no model call.
  • Adaptive sampling chooses the frames sent to the vision model: the first frame of each shot, a base rate (default one frame per second, configurable), and extra samples wherever the cheap signals show a change such as a new object, a camera move or text appearing.
  • Each described frame owns the time range up to the next described frame. Ranges with no visual change are merged instead of being described again.
  • Exhaustive mode describes every Nth frame, down to N = 1, for a chosen asset or time range. A cost and time estimate is shown and checked against the budget before it runs.

72.5 Text storage and search

  • Every level is stored as plain text with asset_id, level, t_start and t_end. Search returns time-coded hits grouped video → segment → frame, each with a thumbnail and a jump-to-timestamp link.
  • description_language is configurable (for example Vietnamese). Transcripts stay in the spoken language. An optional second-language copy lets queries in either language match.
  • Text embeddings of the generated descriptions are stored beside the full-text index, because the wording of a script rarely matches the wording of a caption (73). At personal-library scale they are searched in-process; no separate vector database is introduced.
  • The operator can correct any generated text. Corrections are marked source = human, are never overwritten by re-analysis, and rank above model text.
  • Frame- and segment-level results feed Script-to-Footage Matching (73), Asset Discovery (61.1), the rough cut (74) and reframing (75).

72.6 Execution, privacy and cost

  • Each asset carries a privacy_class: local-only or cloud-allowed. Self-shot footage defaults to local-only until the operator opts in. The Model Router must honour this class, and a local-only asset must never reach a cloud provider.
  • Local speech and vision models for Apple Silicon are candidates only. They must be benchmarked for speed and for accuracy in the operator's language before the design depends on them.
  • Analysis runs as a durable job with a checkpoint after each stage and resumes after restart, sleep or low disk.
  • Results are cached by (checksum, analyzer_version, config_hash). Re-analysis runs only when one of these changes, extending Section 7.3.
  • Before a run, the service estimates frames to describe × unit cost and time, and rejects a run that exceeds the budget. Analysis uses a low-priority background queue.
  • Proxies are disposable under the retention policy. The text understanding is small and is kept.

72.7 Accuracy controls

  • Every generated description stores model and prompt version and a confidence value.
  • Segment and video summaries cite their evidence (frame observation and transcript segment IDs). A statement without evidence is dropped or flagged.
  • People are not identified by default. They are described generically unless the operator labels them, subject to the consent rules of Sections 29 and 67.
  • Quality is measured with a labelled query set (precision@k, Section 35.3) and sampled human review of captions. Thresholds are provisional until measured.

72.8 Visual-only footage

Much of the operator's footage may have no audio track, or audio with no speech. Understanding must then come from the picture alone. The design treats this as a normal case, not an exception: no stage may depend on a transcript.

  • Audio check at ingest: an absent audio track, silence or audio without speech is detected, and the speech stages are skipped rather than failed. Ambient sound, when present, is still labelled (wind, traffic, crowd) as weak context.
  • Motion-aware description: the vision model receives short ordered frame sequences covering a few seconds, not isolated frames, so that it can describe actions and changes — what is happening, not only what is visible.
  • Visual segmentation: moment boundaries come from visual change — a shift in image-embedding similarity between consecutive samples, camera motion, a subject entering or leaving — and are confirmed by the vision model.
  • Image-text embeddings of keyframes are part of the baseline index, so that a script line can be matched against the picture directly, independent of caption wording or caption errors.

73. Script-to-Footage Matching

Purpose: given an approved script, select from the operator's footage library the clips that fit each line — by meaning and context, not by file name or keyword. Deep Video Understanding (72) exists to serve this capability.

73.1 Principle

Script and footage are translated into the same structured description and then compared in stages: broad recall first, careful judgement second, selection across the whole sequence last. Every match is explainable: which requirement of the script line was met by which evidence in the footage.

73.2 What the index must contain

  • Candidate moments: segments are subdivided into moments of usable clip length (configurable, for example 2–20 seconds) with stable content. Boundaries are placed where the content changes — a new action, subject, topic or camera move — even inside one continuous take with no cuts. Matching returns moments, not whole files: from a recording of several minutes, only the few seconds that fit the script line are selected.
  • Role: each moment is classified as a-roll (a person speaking to camera, matched by what is said) or b-roll (matched by what is shown), with finer labels such as establishing, detail, reaction and transition.
  • Descriptors: subjects, actions, setting, time of day, mood, shot size, camera movement and visual quality.
  • Context inheritance: the search text of each moment carries the meaning of its parent segment and the context of its video — where, when and why it was filmed — because the same picture can mean different things in different videos.
  • Text embeddings of the moment descriptions are stored beside the full-text index. Image-text embeddings of keyframes are stored as well, so that footage without speech can be matched on the picture directly (72.8).

75. Subject-Aware Reframing and Multi-Source Sync

75.1 Subject-aware reframing

  • Subject tracks (face, person or salient object) are computed on the proxy as part of tier T3 analysis.
  • A ReframePlan is a keyframed crop window per target aspect ratio (9:16, 1:1, 4:5, 16:9), stored under EditPlan crop_rules.
  • The crop path is smoothed with a dead zone and limits on pan speed and acceleration, to avoid jitter.
  • Modes: static crop, tracked pan, two-subject split or alternation, and fit-with-background when the subject cannot be held in frame.
  • The plan respects platform safe areas and caption zones from the channel profile.
  • QC measures the share of frames with the subject inside the crop, crop jitter and cut-off text. Failures go to review. The original framing is never overwritten.

75.2 Multi-camera and external-audio sync

  • Offsets between sources are computed by audio cross-correlation; embedded timecode is used when present.
  • Drift on long recordings is detected and corrected with piecewise offsets.
  • A SyncGroup stores member assets, offsets, drift and confidence. Low confidence requires human confirmation.
  • When an external recorder is present, its audio is the master track.
  • Angle selection rules (active speaker, wide shot on overlap) produce EditOperations. Alternatively, a synced multi-camera timeline is handed to Resolve where that path has been validated.

78. Music and Sound Design

  • Sources: licensed libraries, operator-owned recordings, and generated music only where the provider terms permit the intended use. Every track is recorded in the Rights & Provenance Ledger before compose (Sections 29.2 and 67).
  • A MusicBrief is derived from the script: mood, energy curve, tempo range, duration, sections, instruments to avoid, and vocal or instrumental.
  • Candidates are searched by metadata and fitted to picture: trimmed or looped on bar boundaries and ended on a natural ending. A beat grid is optional for aligning cuts.
  • A SoundCue is created from each Shot.audio_cues entry (Section 23): type (effect, ambience, foley), description, offset, duration, asset and gain.
  • The mix keeps separate stems for dialogue, music, effects and ambience. Dialogue has priority, with automatic ducking of music under speech.
  • Loudness is normalised to the target in the channel profile, with a true-peak ceiling. Targets are configuration values to be verified per platform.
  • AudioMixProfile, referenced by EditPlan in Section 23, is defined here: stem gains, ducking depth and timing, loudness target, peak ceiling and fades.
  • Stems are retained for re-mixing, localisation and repurposing.
  • QC extends the audio row of Section 26: music masking speech, abrupt music endings and missing cue assets. An unlicensed track is a hard block.
  • The baseline implementation is deterministic FFmpeg audio processing. Finishing in Resolve is optional.

  • Hybrid mode (recommended): bulk indexing — speech recognition, frame description, embeddings — runs locally. Only the script, text descriptions and the keyframes of the top few candidates are sent to the Claude API for script analysis, summaries and judgement.

83. Architecture Decision Record — v3.3

Decisions

  • Video understanding is text-first, time-coded and three-level. It is stored as derived data and indexed with full-text search and text embeddings.
  • No stage depends on a transcript. Footage without speech is a first-class case, understood from motion-aware visual description, image-text embeddings and non-speech context.
  • Footage is matched to a script in stages: recall, model judgement on real keyframes, then selection across the sequence. Unmatched needs are reported as gaps, never filled silently.
  • Frame coverage is achieved by valid-range mapping with adaptive sampling. Exhaustive frame analysis is opt-in and budgeted.
  • Self-shot footage is local-only by default.
  • Footage editing is non-destructive and expressed as EditOperations.
  • Provider clip limits are data in capability profiles; the planner adapts shots to them.
  • Dialogue is produced audio-first. Lip sync is a routed strategy with a restaging fallback.
  • The audio mix is deterministic and stems are retained.
  • The technology stack of Section 82 is adopted as the starting selection, in hybrid local-and-cloud mode where the operator allows it. It becomes final only after the validation spike.

Consequences

  • Proxies and analysis data grow with hours of footage. Storage capacity must be measured and planned before large ingests.
  • Understanding quality depends on model accuracy in the operator's language, which requires a benchmark before commitment.
  • Text embeddings enter the MVP for context B. This narrows the full-text-before-vectors sequencing of Section 36 for this one use; the decision against a dedicated vector database stands.
  • The data model gains entities. Source-footage entities and planned-content entities stay separate.
  • All thresholds, tiers and defaults in this addendum are provisional until validated on representative footage.

Final design position

AI Video Factory v3.3 makes the operator's own footage as searchable as text, selects from it the clips a script needs, and closes the production gaps between a plan and a finished video: cutting by transcript, reframing, synchronising sources, fitting shots to model limits, giving characters a voice, and mixing sound. Each addition is a proposed contract that must be proven on real footage and real providers before it is relied on.

84.4 Dependency rules

  • A layer may call any lower layer and never a higher one.
  • The Experience layer reaches the system only through the API.
  • Domain modules do not call each other. They exchange work through the timeline and shared records, and register their stages with the Orchestrator. The flow is Planning → Sourcing → Edit → Quality → Distribution; Library serves Sourcing and Edit.

  • Every model call goes through the Model Router.
  • Data is read and written through repositories.
  • Policy and budget are enforced in the Platform core when a stage is dispatched, so scheduled and internally spawned work is checked exactly like an API request. The API layer performs authentication and input validation only.
  • These rules are checked automatically by an import-rule linter in the test suite.

85. Platform Core

85.1 Role

The Platform core is the pipeline runtime. It decides operational matters — which step runs next and when, whether to retry or stop, whether budget remains, which model to call. It does not decide content matters such as what a video says or which clip fits a line; those belong to the domain modules and the models they call. Operational behaviour must be deterministic and testable, while model output is not; keeping the core ignorant of video stops the uncertain part from leaking into the part that must be certain.

89.5 Rules

  • Claiming: a worker claims a ready stage by compare-and-swap inside one SQLite write transaction. The claim has an expiry and is extended by heartbeat. One writer wins; the others see no change.
  • Atomicity: a state change and its event are written in the same transaction.
  • Success requires proof: a stage becomes succeeded only after its outputs exist, pass validation and are registered with a checksum.
  • Effect class: every stage declares one of three classes — pure (no external effect; retry freely), idempotent-external (safe to retry with the same idempotency key), non-idempotent-external (for example publishing; never retried without reconciliation).
  • Recovery at start-up and on wake: for each running attempt, check that the worker is alive (process id plus process start time) and its heartbeat is fresh. If not, a pure stage is marked crashed and retried; any other stage is marked unknown and reconciled through its adapter.
  • Retry: each stage has max_attempts and exponential backoff. Reaching the limit moves the stage to blocked, not to an endless loop.
  • Policy and budget: checked when a stage is dispatched. A denial moves the stage to blocked with the reason.
  • Cancellation: the request is recorded first. A running attempt stops at its next safe checkpoint, and its adapter is asked to cancel any external job.
  • Kill switch: no stage with a cost or an external effect is claimed while it is on. Reading status always works.
  • Idempotent submission: a run submitted twice with the same idempotency key is one run.
  • History: attempts are never overwritten. A manual retry of a blocked or failed stage creates a new attempt.

91.3 Versioning and immutability rules

  • An AssetVersion is immutable and identified by its checksum. New content is a new version; a file is never overwritten.
  • Script and Timeline are versioned documents. An edit creates a new version, and an approved version is frozen.
  • A Review binds to the version and checksum it approved. If the content changes, the approval no longer applies.
  • A TimelineItem references an AssetVersion, not an Asset, so that a render can always be reproduced.
  • Derived data — moments, understanding, embeddings — is keyed by (asset checksum, analyzer version, configuration hash) and is regenerated rather than edited. Human corrections are separate records that survive regeneration.
  • Lineage is complete by construction: parent versions and the creating attempt trace any published video back to its sources, models and settings.
  • Rights and privacy propagate: a derived asset takes the most restrictive status of its parents.
  • Identifiers are opaque, type-prefixed and never reused. A file path is never an identity.
  • Records are archived, not deleted. Media files are removed only by the retention policy, and their lineage rows remain.
  • Every record carries created_at, its creator (an attempt or the operator) and a schema version.

91.4 Storage

  • One SQLite database in WAL mode holds all records, the full-text index and the vectors. All writes go through repositories.
  • Original footage is referenced in place and identified by checksum; it is not copied into a managed store, to save disk.
  • Derived and generated files live in a managed media directory addressed by checksum.

95. Narration for Footage without Speech

When footage carries no speech, the narration is the spine of the video. Narration is produced before the picture is cut, because its timing decides how long each clip must be.

  • A narration line is a DialogueLine (77) spoken by a narrator. The narrator has a CharacterVoiceProfile: a synthetic voice, a licensed voice, or the operator's own recorded voice.
  • Order of work: approve the script → produce narration audio with word timings → derive each shot's duration → match footage (73) → cut.
  • The operator may record narration instead. The recording is aligned to the script by speech recognition, and lines that differ from the script are flagged.
  • The pronunciation dictionary of the brand profile (29.1) applies to names and foreign words.
  • Synthetic voice quality in the operator's language is unverified and must be benchmarked before a voice is fixed in a template.

96. Captions and Subtitles

  • Text source: for narration and dialogue, the approved line text with its word timings, which is exact. For speech in footage, the transcript with word timestamps, corrected by the operator where needed.
  • Segmentation rules come from the template: maximum characters per line, maximum lines, minimum and maximum display time, breaks at phrase boundaries, no single orphaned word.
  • A CaptionStyle fixes font, size, colour, outline or background, position and the safe area. The font must cover the diacritics of the caption language.
  • Short-form styles may highlight the current word; this needs word timings and is part of the style.
  • Output: captions burned into the picture for short-form, and a sidecar file (SRT or VTT) for platforms that accept one. Both come from the same CaptionTrack.
  • Translated captions (P1) are a new CaptionTrack in another language, produced by a model and reviewed before use.
  • Operator corrections are stored on the CaptionTrack and survive re-rendering.
  • QC applies the subtitle row of Section 26: timing, readability, overflow, spelling and safe area.

98. Picture Conform and Correction

98.1 Conform

  • Every source is conformed to the project's working format before it is cut: constant frame rate, working resolution, and one working colour space (standard dynamic range, Rec. 709).
  • Variable-frame-rate recordings, common from phones, are converted to a constant rate so that audio stays in sync.
  • HDR sources are detected from their colour metadata and tone-mapped to standard dynamic range. Phone footage is often recorded in HDR; mixing it unprocessed with other sources gives washed-out or blown-out pictures.
  • Log footage is converted with the transform declared in its CameraProfile.
  • Conform is non-destructive: it is a transform on the TimelineItem and is also used when the proxy is made, so that the preview looks like the render.

99. Audio Clean-Up

  • Applies to footage with speech, before the mix of Section 78.
  • Steps: noise reduction, hum removal, levelling of speech. Settings are conservative, because over-processing damages the voice more than noise does.
  • A speech-enhancement model may be used through a model adapter; it is a candidate to be verified, and it must respect the privacy class of the asset.
  • The original audio is kept. The cleaned track is a derived asset version, and the review screen can compare the two.
  • QC checks that speech is intelligible and that no processing artefacts were introduced, by measurement and by sampled listening.

100. Storage Volumes, Offline Media and Automatic Ingest

100.1 Volumes

  • A StorageVolume is a disk known to the system: internal, external or network. An asset version's location is a volume plus a relative path, never an absolute path.
  • Originals stay where they are (91.4). Proxies, thumbnails, understanding and embeddings are kept on the internal managed store, so that search, matching, preview and rough cut all work while the originals are offline.
  • A final render needs the originals. If a required volume is offline, the render stage becomes blocked with the list of volumes to connect. A draft render from proxies is available and is marked as draft.
  • Relinking: when a volume appears at a new path or files were moved, assets are recognised by a quick fingerprint (size plus partial hash) and confirmed by full checksum.
  • A missing-media report lists assets whose originals can no longer be found on any known volume.
  • Free space is checked before ingest and before render. Proxy size is governed by a policy that must be set from measured sizes per hour of footage.

100.2 Automatic ingest

  • Watch folders and volume-mount detection start an ingest run when new media appears.
  • A file is ingested only after it has stopped changing, so that a copy in progress is not read.
  • Duplicates are recognised by checksum and linked, not ingested twice.
  • An ingest preset per source sets the CameraProfile, the privacy class and the analysis tier.
  • After a session is ingested, the operator is asked once for the optional session note of Section 72.8.

101. Library Extras

  • Find similar: from any moment, list the nearest moments by image-text embedding. This reuses the index of Section 72 and needs no new analysis.
  • Usage tracking: a UsageRecord is derived from the timeline items of every published render. The library can show which footage has never been used.
  • Reuse policy: matching (73) applies a configurable penalty to moments used recently in other videos, so that the same clip does not appear everywhere.
  • Ratings: the operator can mark a moment as favourite or as rejected. Matching treats this as a prior; a rejected moment is never proposed.
  • Collections: named groups of assets or moments chosen by the operator, usable as a search filter and as a restriction for matching.

102. Generated-Video Enhancement and Character Models

102.1 Upscaling and frame interpolation

  • Generation providers often return clips below the output specification in resolution or frame rate. An enhancement stage brings a clip up to the specification.
  • Enhancement runs only on clips that were selected, never on every candidate, to control cost.
  • The enhanced clip is a new asset version whose parent is the provider's output.
  • QC checks for added artefacts, flicker and changes of identity; a failed enhancement falls back to the original with a recorded limitation.
  • Enhancement models, local or cloud, are candidates to be verified through the adapter conformance tests.

102.2 Character model training (P2)

  • Entry condition: a recurring series, and a measured continuity violation rate (Section 65) that reference images alone cannot bring under the threshold.
  • A character-specific model is trained from the approved reference set. Training needs a GPU and therefore a cloud resource.
  • A CharacterModel is versioned and records its training set, provider, settings, and the rights and consent that cover it.
  • A new model version passes the continuity evaluation before the Model Router may use it.

108.2 How a tool is called

  • Each OpenMontage tool runs in a separate child process with its own Python environment. NEXORA sends the request as JSON and receives the result as JSON.
  • OpenMontage is pinned to a specific commit and upgraded deliberately, never automatically.
  • A NEXORA adapter wraps the call and supplies what Section 90 requires and the tool lacks: a time limit, cancellation by stopping the process, a cost record taken from the tool's result, and normalised errors.
  • The tool is told where to write. Outputs go to the staging area; NEXORA validates them, computes checksums and registers them as asset versions.
  • Credentials are passed to the child process for that call only. The OpenMontage environment file is not used.
  • All code that touches OpenMontage lives in one package, so that it can be replaced as a unit.

Separate processes give three benefits: the heavy dependencies of OpenMontage do not mix with NEXORA's, a tool that hangs cannot take the system down, and all AGPL code sits in one place.

108.5 Points to watch

  • Some tools, especially composition, expect OpenMontage's own project files. Such a tool is either given a temporary project directory that is discarded afterwards, or it is not called and NEXORA's own composition is used.
  • OpenMontage keeps its own clip cache under the user's home directory, and downloaded models have their own caches. These must be disabled or pointed at storage that NEXORA manages, so that nothing is stored twice on a disk with little free space.
  • Each heavy model runs in its own process and takes its own memory. On a machine with 24 GB the Platform core allows one heavy model at a time, and a child process exits as soon as its work is done.
  • That each tool is truly stateless is an assumption taken from OpenMontage's tool contract. It must be checked tool by tool when the tool is integrated.

  • A stock clip and a generated clip obtained through OpenMontage appear in library search with their origin, licence or model, and understanding.
  • Replacing the OpenMontage package with another implementation of the same adapters requires no change in any domain module.

111. Reducing Review Load

Pipeline B has up to five human gates and pipeline A up to seven. At several videos a day the operator becomes the bottleneck. The aim is review by exception: the operator sees what the system is unsure about, not everything.

  • Gate policy: each gate in a format template is set to required, confidence-based or off.
  • Confidence-based acceptance: an item is accepted without review only when every must-have passes, the judge score is above a threshold, the margin over the runner-up is above a threshold, and nothing is flagged for rights, privacy or risk. Otherwise it is queued.
  • Graduation: confidence-based acceptance is enabled for a gate only after the operator's recorded decisions agree with the system's first choice at a target rate over an agreed number of decisions (MatchFeedback, 73.6). Thresholds start strict.
  • Combined review: one screen walks script, clips and preview together and highlights only the low-confidence items.
  • Batch review across projects, so that similar decisions are taken together.
  • Sampling audit: a share of auto-accepted items is still shown to the operator, to detect drift; a fall in agreement switches the gate back to required.
  • Never automatic: approval of a final render before publishing, unknown rights, high-risk topics, and the policy cases of Section 42.
  • Measured by operator minutes per finished minute and by the number of gates touched per video.

112. Incremental Render and Fast Preview

If changing one clip re-renders the whole video, the fix-and-review loop is slow and the operator stops fixing. Render work is therefore cached per timeline item.

  • Render unit: each TimelineItem is rendered on its own to an intermediate file with all its picture transforms applied.
  • Cache key: the asset version checksum, in and out points, transforms, output specification and tool versions. An unchanged item is never rendered again.
  • A transition between two items is rendered as its own short segment, keyed by both neighbours.
  • Captions and graphics are composited per segment, so only segments whose overlay changed are re-encoded.
  • Audio is mixed separately from stems and joined at the end; a picture change does not re-mix audio, and an audio change does not re-render picture.
  • The final file is assembled from cached segments. QC always runs on the assembled file.
  • Preview uses the same graph on proxies at low resolution. The target preview time is to be set from measurement.
  • The segment cache is derived data under the retention policy. The intermediate format is chosen from measurement, weighing speed against the limited disk.

113. Keyframe-First Generation

  • A generated shot starts from an approved still image. Images cost far less than video, so mistakes in composition, character and style are caught before video is paid for.
  • The still is generated with the approved character, location and style references (61.1) and reviewed on the filmstrip of the board.
  • The approved still is the first frame for image-to-video generation and the continuity anchor of the shot. For a split shot, the last frame of one sub-shot is the first frame of the next (76).
  • A correction at the still stage — pose, framing, wardrobe — is made by editing the PromptSpec (114) and regenerating the still only.
  • Exception: when a provider offers text-to-video only, a small number of low-resolution drafts replaces the still.

115. Keyword-Timed Picture

  • Each ShotNeed carries anchor words: the words of the line that the picture illustrates, with their times from the narration.
  • The picture change lands at the anchor word or slightly before it; the lead is set in the format template.
  • Inside the chosen clip, the moment where the action is clearest is aligned to the anchor word, using the frame observations of the moment.
  • A line with several anchor words may receive several inserts, subject to the template's minimum shot length.
  • Cut points snap first to phrase boundaries of the narration, then to a music beat when one lies within tolerance (78). A cut never falls inside a word of on-camera speech.
  • QC measures the offset between each anchor word and its picture change.

116. Ideas from the Footage Library

  • Because the library is understood, the system can answer: what videos can be made from what has been shot?
  • Moments are grouped by theme, place, time and shooting session, with attention to footage that has never been used (101).
  • Each proposal is an IdeaCandidate (22) with a title, an angle, a fitting format template, the moments that would carry it, the share of shots the existing footage covers, the expected gaps and an estimated duration.
  • Proposals are scored on footage coverage, freshness, novelty against published videos, and fit with the brand profile.
  • Triggers: after a new session is ingested, on request, and periodically.
  • An accepted proposal becomes a pre-filled brief and enters pipeline B at stage 1.
  • The work is done by a bounded agent in the Strategist role (30, 86).

A render is not ready to publish until it has a thumbnail, a title and a description. Earlier sections only checked that these exist (26); this section produces them. Controlled testing of alternatives remains the Packaging Optimizer of Section 51.

Part

How it is produced

Thumbnail

Candidate frames are taken from the render and ranked on sharpness, composition and a clear subject. A designed thumbnail may add title text through the graphics renderer, in the thumbnail style of the format template. Several candidates are offered; the operator chooses.

Title

Several options generated from the script and the understanding of the finished video, within the platform's length limit.

Description

Summary, key points and chapter timestamps taken from the timeline.

Tags

From the script's themes and the channel profile.

Credits

Attribution lines generated from the Rights & Provenance Ledger for every asset whose licence requires attribution.

Disclosure

A synthetic-content flag set automatically when lineage shows generated picture or voice (67).

Captions

The sidecar file of the CaptionTrack (96).

  • The parts form a PublishPackage tied to one render and one channel, sized to the platform specifications in the channel profile.
  • A thumbnail and a title must represent the video truthfully; a misleading package is a policy failure (51).
  • The package is reviewed with the render. While publishing is done by hand, it is exported with the video file.

120. Still Images as Source Material

  • The operator's photographs are ingested into the Library like footage: checksum, capture date, location and device from their metadata, and volume and session.
  • Each image is understood as text — caption, objects, people count, setting, visible text — and receives text and image-text embeddings. In the index an image is a moment without a time range.
  • Matching (73) treats images as candidates of role still. The format template sets the largest share of stills a video may contain.
  • On the timeline a still receives a camera move — a pan or zoom path computed from its subject, reusing the subject detection of Section 75 — and a duration taken from the narration.
  • Phone formats are converted at ingest, orientation is honoured, and HDR photographs are tone-mapped as in Section 98.1. A photograph with an attached short clip is ingested as video.
  • A photograph may also be the first frame for image-to-video generation (113); the result is then a generated asset and carries the synthetic-content disclosure.
  • The whole-video review scores stills risk (117), so that a video does not turn into a slideshow.

121. Music Library Understanding

  • Music the operator owns or has licensed is ingested as assets of kind music, each with its licence record.
  • Analysis produces: duration, tempo, beat grid, sections (intro, build, peak, close) from changes in energy, loudness, whether vocals are present, and mood, genre and instrument labels with a short text description.
  • The description is indexed as text and embedded, so music is searchable in words like footage.
  • A MusicBrief (78) is matched against this index: filtered by tempo range, duration and vocal policy, ranked by mood, and fitted using the section boundaries.
  • The beat grid feeds cut snapping (115).
  • Usage is tracked so that one track is not repeated across consecutive videos, and a licence that has expired removes the track from matching.
  • The analysis tools and the audio-labelling model are candidates to be verified.

122. Environment Check

The system depends on tools, models and storage that differ from machine to machine. An environment check reports what is present and what each gap disables, so that a pipeline refuses a stage it cannot complete instead of failing in the middle.

Checked

Examples

Media tools

FFmpeg version, its filters and encoders, the graphics renderer, shot detection.

Models

Which local models are installed and their versions; which cloud providers have credentials.

Integration

The pinned OpenMontage commit and its environment; whether DaVinci Resolve is installed, running and scriptable.

Resources

Free disk on each volume, memory, which volumes are online.

Configuration

Templates, voice profiles and channel profiles that refer to something missing.

  • The result is a capability matrix: each pipeline stage is available, degraded or unavailable, with the reason and how to fix it. Adapters contribute through describe (90.1).
  • It runs at start-up, on request and as a preflight before a run. A stage whose requirements are unmet becomes blocked with the reason.
  • It is shown on the Home and Settings screens.
  • Known findings on the target machine (82.3, 106.5) are its first test cases: the FFmpeg build lacks text and HDR filters, and free disk is low.

123. The Operator's Own Voice

  • Purpose: narration in the operator's own voice without recording every script.
  • Consent: by default only the operator's own voice may be cloned. A consent statement and the sample recordings are stored. Any other person's voice requires their documented consent (67).
  • Creation: a guided recording session in quiet conditions; the samples are checked for noise and clipping; the voice is created with a provider or a local model, both candidates to be verified.
  • The result is a CharacterVoiceProfile with voice source cloned, a consent reference and the provider's terms recorded.
  • Sending voice samples to a cloud provider is a privacy decision: the profile is created only if the operator allows it, and the procedure to delete the voice at the provider is recorded.
  • Evaluation before use: similarity and intelligibility by listening, and pronunciation in the operator's language with the pronunciation dictionary (29.1).
  • The cloned voice is usable only in the operator's projects, and synthetic-voice disclosure is applied where a platform requires it.
  • Fallback: narration recorded by the operator and aligned to the script (95).
